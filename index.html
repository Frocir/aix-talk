一个核心认知：AI 时代，人的价值在「两端」

THE BIG IDEA
1 定义 · 你这一端想清楚要什么

把需求、约束、验收写清楚——这就是给 AI 的规约 / Spec。

2 AI 黑盒 · 中间它来写、来生成

跑通、出方案、写代码，它越来越快，但不负责任。

3 验证 · 你这一端判断对不对

测试加人工把关：结果好不好、对不对味，你定。

写完 ≠ 做好：AI 能吐出代码，但「好不好、对不对」要人判断。
做好 ≠ 交付：能跑不等于能上线、能负责，还要看协作与责任。
TAKEAWAY所以该练的不是手速，是把「什么算做对了」说清楚。

一套主流方法：SDD，规格驱动开发

SPEC-DRIVEN DEVELOPMENT
GitHub Spec Kit · 公开标准
笑点所谓 vibe coding，翻译得准确一点是「凭感觉提交，凭运气上线」

别被名词吓到：它公开、规范，而且很好学

OPEN STANDARD · EASY TO START
GitHub / Thoughtworks · 公开资料
谁在定义GitHub · Spec Kit

2025 年开源的官方工具包，五阶段流程、模板、检查清单一应俱全，且明确可离线运行。

谁在拆解Thoughtworks

Birgitta Böckeler 在 Martin Fowler 网站把它分成三级成熟度，也诚实写出代价：小需求别上重流程。

谁在做轻Kiro / OpenSpec

AWS Kiro 走「需求 → 设计 → 任务」；OpenSpec 用提议 → 实施 → 归档的轻量循环。

三级成熟度：spec-first（用完即弃）→ spec-anchored（随代码维护）→ spec-as-source（只改规格）。大多数团队在前两级。
TAKEAWAY上手就三步：建一个 specs 目录，写三个 Markdown，每步自己审一遍再放行。

不能联网、算力也有限时，什么方法最可行？

OFFLINE · LIMITED RESOURCES
公开工程场景 · Air-Gapped
互动模型不能联网、算力也有限，第一件该补的是什么？
一个常被忽略的前提：很多真实研发环境是内网隔离的，模型不能联网，算力和上下文预算也都有限。这时候「换个更强的联网模型」根本不是一个选项。
约束一模型看不到外面

拿不到最新文档，也读不到仓库之外的资料；一知半解时最容易凭空补细节。

约束二试错很贵

上下文有限，反复试错的代价远高于先把话说清楚。

出路把上下文搬进仓库

用本地知识库 / Repo Wiki 沉淀项目现状与术语，再用结构化 Spec 写清本次需求。

TAKEAWAY不是更大的模型，而是「让仓库有记忆」+「把需求写成 Spec」。

一个提醒：规约也会腐烂，要分层、要维护

KEEPING SPECS ALIVE
腾讯架构师联盟 · 公开分享
金句文档有两种死法：没人写，和所有人都写；第二种看起来更健康
两个退化结局：都不提交 → 只留在个人电脑，人一走就丢；都提交 → 人人一套、没有标准，越堆越多没人敢用。做过小组项目就懂了。
Principles原则层 · 项目宪法

安全红线、合规要求、架构原则。改动极少，是最高权威。

Living Specs活规格层 · 当前真相

按领域组织，描述系统现在应有的行为，随需求更新。

Feature Delta增量层 · 本次变更

这次改了什么、为什么改，用完即归档。

维护四件事：有归属（谁的孩子谁抱走）· 有节奏（按层更新）· 有出口（用完即归档）· 有校验（漂移即告警）。
TAKEAWAY判据只有一句：新来的人读得懂，AI 用得上。
